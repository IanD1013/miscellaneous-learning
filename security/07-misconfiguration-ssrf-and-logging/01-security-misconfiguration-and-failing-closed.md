一个 API 即使其团队编写的代码中没有任何漏洞，也可能在上线后很容易被攻入。
设想一个刚部署的 API，仍然保留着安装程序和项目模板设置的内容：一个用户名为 `admin`、密码也是 `admin` 的账户，调试模式处于开启状态，还有一个向任何人列出其文件的文件夹。
这类不安全的设置称为**安全配置错误（security misconfiguration）**，即 OWASP Top 10 中的 A02:2025 Security Misconfiguration。
团队自己编写的代码有一个相关的弱点，由 A10:2025 Mishandling of Exceptional Conditions 涵盖：当检查无法完成时，它会怎么做。
代码可能**失败时放行（fail open）**，即在这种情况下让请求通过，也可能**失败时拒绝（fail closed）**，即拒绝该请求。

### 暴露应用的设置

**默认凭据（Default credentials）**是安装程序在任何人选择自己的凭据之前创建的用户名和密码。
`admin`/`admin` 这一组合出现在安装程序的文档中，是攻击者最先尝试的凭据，因此任何到达管理面板登录页面的人都能在第一次尝试时登录。
将密码存储为加盐哈希（salted hash）没有帮助，因为攻击者输入的是密码本身；在几次密码错误后锁定账户也没有帮助，因为第一次输入就是正确的。
只接受来自公司网络的连接，限制的是哪些机器能访问该面板，而不是谁在使用这些机器：攻击者例如通过钓鱼邮件控制了一台员工笔记本电脑，就能像任何员工一样访问它。
尚未存放任何客户数据的新安装也不例外，因为管理员账户控制着 API 本身以及它之后提供的一切内容。
应将更改或禁用默认账户作为安装过程的一部分。

**调试模式（Debug mode）**会让应用在出现异常时返回一个供开发人员查看的页面。
该页面显示**堆栈跟踪（stack trace）**，其中指明了框架和出错代码所经过的库、服务器上的文件路径以及出错的那一行，并且根据框架的不同，它还可能显示版本号、配置值以及数据库连接字符串之类的机密信息。
仅堆栈跟踪就能告诉攻击者应该去查找哪些软件，因此删除或加密连接字符串仍会留下大部分泄露的信息。
在生产环境中，应关闭调试模式，向用户显示带有参考 ID 的通用错误消息，并将异常详情以相同的 ID 写入服务器日志，当用户引用该 ID 时，团队就能在日志中找到这些详情。
由请求控制的开关，例如 `?debug=true` 查询参数，会将详情交给任何添加它的人。
在 JSON 响应体中返回异常消息和堆栈跟踪的 API，泄露的细节与 HTML 页面相同。

接下来是已经开启却没有人使用的功能。
**目录列表（Directory listing）**会用一个链接了文件夹中所有文件的页面来响应对该文件夹的请求，例如 `/uploads/`，因此任何人都可以找到并下载每一个上传的文件，包括仅供上传者本人查看的文件。
安装程序会添加示例应用，项目模板会添加示例端点，例如一个报告应用版本以及它所使用的每个库的版本的状态端点。
已启用的端点属于攻击面的一部分，即使没有任何客户端调用它：任何发送请求的人都会运行它的代码，其中的任何漏洞都可能被利用。
它不需要链接就能被发现，因为示例路径和模板路径众所周知，攻击者会直接请求它们。
仅执行读取的端点也可能泄露信息。
库已发布的版本是公开的，但此部署运行的是哪些版本并不公开，而这会告诉攻击者应该尝试哪些已公布的漏洞。
应关闭或移除没有用户、客户端或其他系统需要的内容。
有其他东西依赖且不会泄露任何信息的功能应予保留，例如负载均衡器调用的、仅返回 `OK` 的健康检查端点，或用户忘记密码时打开的密码重置页面。

A02 还涵盖缺失或不安全的浏览器安全设置：发送的响应缺少应用所依赖的安全标头，例如 `Content-Security-Policy`，就是其中一种；而将收到的任何 `Origin` 原样复制到 `Access-Control-Allow-Origin` 的 CORS 配置则是另一种。

### 当检查无法完成时

API 通过询问**策略服务（policy service）**来检查用户是否可以修改某个文档，策略服务是一个单独的服务，保存权限规则并回答真或假。
有时它无法给出答案：它宕机了、调用超时了，或者检查所需的某项设置缺失。
检查仍然必须返回某个值，而在问题持续期间，该值决定了谁能进入。
下面是删除文档的检查：

```csharp
public async Task<bool> CanDeleteAsync(int userId, int documentId)
{
    try
    {
        return await policyClient.CheckAsync(userId, documentId, "delete");
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Policy check failed for document {DocumentId}", documentId);
        return false;
    }
}
```

当策略服务给出答案时，该方法返回它的答案。
当它没有及时答复时，客户端会抛出超时异常。
`await` 等待调用完成，而超时的调用会以抛出异常的方式完成，因此异常会传到这个方法。
`catch (Exception)` 会捕获所有异常，包括超时，`LogError` 将其写入服务器日志供团队查看，用户看不到。
随后该方法以 catch 块返回的值正常返回。
请求不会以 500 错误结束；它会继续进行，就好像策略服务给出了那个答案一样。

这个 catch 块返回 false，因此该检查是失败时拒绝：在策略服务宕机期间，没有人能完成该服务本会拒绝的删除。
把这一行改成 `return true;`，检查就变成失败时放行：在服务中断期间，每一次删除都会通过，包括该服务本该拒绝的那些删除，而能够拖慢服务直到其调用超时的攻击者，也能故意获得同样的放行。
失败时拒绝就是将默认拒绝（deny by default）应用于错误：当代码无法确认请求被允许时，就拒绝它。

失败时拒绝是有代价的。
在服务恢复之前，服务本会允许的用户会被拒绝，而这是正确的取舍，因为返回 true 是以一次性放弃所有权限规则来换取可用性。
记录通过了什么的日志无法弥补这一点：日志只记录一次编辑而不能撤销它，而未经许可被读取的文档仍然是被读取过了。
每个权限检查都应失败时拒绝，包括针对普通操作的检查。
用户编辑他人的文档，正是编辑检查要阻止的情形。

### 缺失的设置

缺失的设置也是一种异常情况。
在 .NET 中，读取设置中遗漏的配置键会得到 `null`，除非应用自己的启动代码检查该键，否则应用会正常启动并照常运行。
为了让本地开发在没有策略服务的情况下也能运行而编写的检查，可能会这样开头：

```csharp
var policyUrl = config["Policy:Url"];
if (policyUrl is null)
    return true;
```

如果生产环境的设置遗漏了 `Policy:Url`，每个权限检查都会不询问任何人就返回 true，而且看起来一切正常。
任何在所需设置缺失时跳过自身的检查，都会以同样的方式失败时放行。
要做到失败时拒绝，应在那里返回 false，或者在应用启动时检查该设置，并以指明缺失键的错误来停止应用。

开启错误详情的设置需要同样的谨慎：缺失的值必须落在安全的一侧。
Express 应用将错误传递给错误处理程序，该处理程序通常会记录错误，然后答复调用方：

```js
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: 'Internal server error' });
});
```

`console.error` 写入服务器自身的输出，该输出留在服务器上，因此完整的错误可以放在那里。
只有响应会到达调用方。
应用经常在开发期间将错误消息和堆栈跟踪添加到该响应中，并通过 `NODE_ENV` 环境变量区分开发环境和生产环境。
服务器启动时没有设置的变量读取为 `undefined`。
写成“非生产环境”的条件 `process.env.NODE_ENV !== 'production'`，对 `undefined` 为真（`!=` 的结果相同），因此在没有该变量的情况下启动的服务器会显示堆栈跟踪。
当变量缺失时，`process.env.NODE_ENV === 'development'` 为假，因此只有在设置明确要求的地方才会出现详情。
将该变量添加到部署脚本中可以修复由该脚本启动的服务器；而代码中的条件决定了每一台没有该变量而启动的服务器的行为。
