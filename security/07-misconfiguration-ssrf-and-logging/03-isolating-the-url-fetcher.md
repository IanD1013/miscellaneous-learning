某聊天服务将其消息保存在一个 SQL 数据库中，并为每个发布的链接显示预览，因此 preview worker 会抓取任何用户都可以指定的 URL。
针对服务端请求伪造（SSRF）的目标检查决定了该 worker 拒绝哪些 URL，但只要漏掉一种情况就足够致命：比如以检查机制无法识别的形式编写的内部地址，或者有人重新启用了重定向。
Worker 在哪里运行，决定了这种疏漏的代价有多大。
如果将其运行在消息数据库旁边的私有网络中，它访问数据库就如同访问任何网站一样容易。
而**网络隔离（Network isolation）**则将它运行在一个单独的网络中，在这里是公共网络。
该网络的策略限制了 worker 的**出站流量（egress）**，即限制其可以建立的连接，只允许访问互联网、从中获取任务的队列，以及保存缩略图的存储服务。
如此一来，无论 worker 的代码如何决定，网络都会拒绝与数据库建立连接。

这就是网络访问的最小权限原则。
Worker 在每次抓取前仍然会运行目标检查，因为网络策略并不能覆盖每一个地址：在 AWS、Azure 和 Google Cloud 上，服务器可以从其运行的任何网络访问其位于 169.254.169.254 的自身元数据端点，因为网络规则不适用于该地址。

设计的其余部分：

- 聊天客户端（Client / User 模块）通过 API 网关将每条消息发送到聊天服务（Service），后者将其存储在消息数据库（Database (SQL)）中。
  聊天服务和数据库都在私有网络中运行。
- 对于每个链接，聊天服务都会在消息队列上放置一个包含该 URL 的预览任务。
  预览 worker（Worker / Background Job）连接到队列并请求其下一个任务。
- 聊天服务从对象存储中读取每个缩略图，该连接由其自身从私有网络内部向外发起。

任务在队列中单向传递：聊天服务放置任务后即继续处理其他事务，不会通过该途径返回任何回复。
Worker 也从不连接到聊天服务，甚至连通知预览已就绪也不会连接。
允许 worker 访问聊天服务的策略，同样也会放行携带聊天服务地址的已发布 URL，因为网络无法区分是 worker 的正常报告，还是攻击者要求的抓取请求。
私有网络中的每个地址都是如此。
Worker 获取每个任务都要连接到队列，因此如果队列位于私有网络内部，该网络的策略就需要配置一条例外规则，以允许 worker 跨越信任边界。
请将队列保留在私有网络之外：即使包含队列地址的已发布 URL 依然能通过，但它只能访问该队列，而且私有网络会拒绝来自 worker 的所有连接，无需维护任何例外规则。

### 在画布上

将 Private Network 和 Public Network 区域并排放置。
在此画布上，绘制在另一个区域内的区域会被视为其一部分，因此将一个区域嵌套在另一个区域内会使内部区域的模块同时处于两个网络中。
队列和对象存储应属于 Public Network 区域或位于这两个区域之外，而发布 URL 对应的站点（External API 模块）应位于这两个区域之外。
API 网关可以放在任意一个区域内，也可以放在两个区域之外。

从发起连接的组件开始绘制每条连接线，但有一个例外：队列与 worker 之间的连线指向任务传递的方向，即从队列指向 worker，尽管实际上是由 worker 发起的该连接。
