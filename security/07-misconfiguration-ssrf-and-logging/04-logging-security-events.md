完整记录每个请求，包括请求体和标头，看起来像是保留所有证据的办法。
但同一份日志中也会保存每个登录表单中的密码和每个 `Cookie` 标头中的会话 ID，而显示攻击的寥寥几行则淹没在数百万个普通请求之中。
安全日志则是有选择性的。
它只记录**安全事件（security events）**：防御者需要在攻击发生时察觉攻击，或在事后重建攻击所需的事情。
每个事件都写成由选定字段组成的简短条目，而不是请求的副本。

### 记录什么

应用会记录以下安全事件：

- **登录**，包括成功和失败。
  针对同一个账户的一连串失败就是密码猜测的样子，而这一连串失败之后的成功可能就是猜测者闯入的时刻。
- **访问检查拒绝的请求**，例如用户试图删除另一个用户的账户。
- **输入验证失败**：服务器的检查拒绝的值，例如在期望数字的路由上出现值为 `1 OR 1=1` 的订单 ID。
  探测 SQL 注入的人会产生许多这样的事件。
- **管理员更改**，例如给用户赋予新角色。

这些条目按时间顺序保存，就是应用的**审计跟踪（audit trail）**，团队可以据此重建攻击者尝试了什么、何时闯入以及更改了什么。
普通流量不进入安全日志。
对公共页面的匿名访问并不表明存在攻击，搜索耗时是性能数据；两者都属于其他日志或指标，放进安全日志只会淹没事件。

每个条目回答四个问题，遗漏其中一个的条目以后就无法回答该问题：

- **何时（When）**：时间戳，写入条目中。
- **应用中的何处（Where）**：路由或功能，例如 `/orders/7`。
- **何人（Who）**：用户 ID（登录时为所尝试的用户名）以及请求的来源地址。
  会话 ID 不能替代它，下一节会解释原因。
- **何事（What）**：事件和尝试的操作，例如针对 `action=delete` 的 `access_denied`。
  像“Request forbidden”这样的简单消息只说明某件事被拒绝了，而没有说明是什么事、在哪里。

当访问检查拒绝请求时，应用会做两件事。
它拒绝该请求，并用一条简短的消息告诉用户该操作不被允许，仅此而已，因为堆栈跟踪或拒绝他们的规则会向攻击者展示检查的工作方式。
并且它会写入一条包含全部四个字段的 `access_denied` 条目。
检查必须失败时拒绝：记录拒绝后又让请求通过，无论出于什么原因，都是失败时放行，而日志最终记录的是该检查本来要阻止的那次删除。

### 密码、会话 ID 和令牌

密码、会话 ID、令牌和密钥绝不能写入日志。
日志会被复制，并被广泛阅读：被其他员工阅读，被收集和搜索日志的服务阅读，也被任何入侵其中之一的人阅读。
被记录的密码会让读到它的人能够登录。
被记录的会话 ID 本身就足够了，因为服务器仅凭该 ID 就能识别已登录的用户，因此一份副本就能在没有密码的情况下接管正在进行的会话。
在数据库中对密码做哈希只保护存储的哈希值；日志从登录表单中取得的副本是明文。
将日志文件限制为团队自己的账户访问，缩小了谁能读取它们的范围，但每个拥有该访问权限的人，以及任何接管其中一个账户的人，手中仍然握有可用的凭据。

### 换行符与日志注入

纯文本日志每行保存一个条目，因此**换行符（line feed）**字符是区分一个条目与下一个条目的标志。
JavaScript 和 C# 代码将其写作 `\n`。
Windows 文本文件以回车符和换行符结束每一行，写作 `\r\n`，日志修复需要同时处理这两个字符。
下面这个处理程序会记录其输入检查拒绝的每个订单 ID：

```js
fs.appendFileSync('security.log', `${new Date().toISOString()} Rejected order ID ${orderId}\n`);
```

攻击者发送一个订单 ID，它由 `7`、一个换行符，以及 `2026-10-18T07:30:00.000Z Role changed to admin for user 1187` 组成，后者模仿了应用记录真实角色变更的方式。
文件因此增加了两行：

```text
2026-10-18T07:29:58.412Z Rejected order ID 7
2026-10-18T07:30:00.000Z Role changed to admin for user 1187
```

这就是**日志注入（log injection）**，也称为日志伪造（log forging）：输入中的回车符或换行符会开始新的一行，因此攻击者添加了一个看起来与应用所写完全一样的条目。
该值中包含的是字符本身，而不是一个反斜杠加一个 `n`：URL 将其携带为 `%0A`，服务器会将其解码为一个换行符。
浏览器中的检查无法阻止这一点，因为攻击者无需页面就能发送请求。
途中也没有任何东西会清理该值。
`appendFileSync` 会写入所给字符串的每个字符，包括换行符，而 Node.js 不知道哪一部分来自请求。
将日志保持在内部也没有用：攻击者从不需要读取它，只需发送一个其值会落入日志的请求。

日志注入与 SQL 注入是同一类漏洞：输入携带的字符在其落入的格式中具有特殊含义。
与页面中的输出编码一样，修复方法是处理在该值落入之处具有特殊含义的字符，而在日志行中，这些字符就是回车符和换行符。
**结构化日志（Structured logging）**可以做到这一点。
每个条目是一组具名字段，这里是每行一个 JSON 对象，输入放在它自己的字段中：

```js
const entry = {
  time: new Date().toISOString(),
  event: 'validation_failed',
  route: '/orders',
  user: userId,
  ip: clientIp,
  orderId: orderId,
};
fs.appendFileSync('security.log', JSON.stringify(entry) + '\n');
```

`JSON.stringify` 会将字符串中的换行符写成两个字符 `\n`，将回车符写成 `\r`。
对象后面添加的 `'\n'` 是唯一真正的换行符，用来结束该条目，因此同样的攻击现在停留在一行之内：

```text
{"time":"2026-10-18T07:29:58.412Z","event":"validation_failed","route":"/orders","user":5521,"ip":"203.0.113.7","orderId":"7\n2026-10-18T07:30:00.000Z Role changed to admin for user 1187"}
```

必须保持纯文本的日志，可以改为在写入之前替换输入中的每个回车符和换行符。
保持换行符原样的更改毫无作用。
`trim()` 只会删除文本开头和结尾的空白，因此中间的换行符会保留。
将写入改为 `console.log` 看起来更安全，但 `console.log` 也会将其文本中的换行符输出为新的一行。
另一个想法是将订单 ID 放在时间戳之前，这样伪造的行就不能以看起来真实的时间开头。
换行符之后的文本仍然是攻击者从第一个字符开始书写的新行，因此无论字段以什么顺序出现，它都可以模仿应用的格式。

### 对重复失败发出警报

日志条目本身不起任何作用：写入它既不会减慢下一次尝试，也不会阻止该地址，也不会通知任何人。
如果没有人阅读日志，也没有任何东西监视它，脚本就可以在一夜之间对一个账户尝试数千个密码，闯入其中，并留下一份完整的记录，几天后才有人发现，甚至永远不会被发现。
重复的失败，例如几分钟内针对同一个账户或来自同一个地址的多次登录失败，应该触发**警报（alert）**：在攻击仍在进行时就送达某个人的通知。
A09:2025 Security Logging and Alerting Failures 是 OWASP 针对这两种缺口的类别：从未被记录的事件，以及从不发出警报的日志。
