reports 服务将其数据库密码保存在 `/etc/reports/db.env` 中，表现为一行 `DB_PASSWORD=`。
该文件的所有者和所属组为 root:root，权限模式为 644，最后的 4 让机器上的每个账户都能读取它。
`/etc/reports` 的权限是 755，因此每个账户也能列出该文件夹中的内容。
位于 `/etc` 下并不能隐藏任何东西：任何账户都可以运行 `ls /etc` 并查看里面的内容。
旁边还有一个副本 `db.env.bak`，具有相同的密码和相同的权限模式。

### 所有者 root，所属组 reports，权限模式 640

供服务读取的**机密文件**应将所有者设为 root，所属组设为该服务所在的组，权限模式设为 640。
其中 6 允许 root 读取和修改它，4 允许该组的成员读取它，而 0 则将其他所有账户拒之门外。
reports 服务以 reports 账户运行，该账户的组是 reports，因此它可以读取自己的密码但无法修改。
这就是文件的最小权限原则：服务获得了读取权限，这也是它唯一需要的权限。

将 reports 账户设为所有者看起来限制得更严，但文件的所有者始终可以对其执行 chmod，因此拥有自身机密文件的服务可以重写它或向所有人公开。
而将其所属组设为 root 且权限模式设为 600 则走向了另一个极端：该服务根本无法读取该文件。
该文件夹应设置相同的所有者和所属组，权限模式设为 750，这样该组就可以打开它，而其他账户既不能列出其内容，也无法访问其中的任何文件。

### 新文件与 umask

chown 和 chmod 用于修复已存在的文件。
对于新文件，则由 **umask** 决定：它列出了在你的 shell 中运行命令所创建的每个新文件被剥夺的权限。
在你的主文件夹中尝试一下：

```text
$ umask
0022
$ touch notes.txt
$ ls -l notes.txt
-rw-r--r-- 1 learner learner 0 Oct 18 12:00 notes.txt
```

22 移除了所属组和其他用户的写权限，因此新文件的初始权限为 644（所有账户可读），新文件夹的初始权限为 755。
如果将密码写入一个新文件，随后再运行 `chmod 640`，这期间文件都是可读的。
Linux 仅在打开文件时检查权限，因此在此瞬间打开了该文件的程序在 chmod 之后仍可继续读取。

### 使用 install 创建机密文件

`install` 将一个文件复制到另一个路径（按此顺序指定）。
它在创建副本的同时，使用 `-m` 设置其权限模式，使用 `-o` 设置其所有者，使用 `-g` 设置其所属组，因此副本在整个过程中都不会被其他账户读取。
要在不先将密码写入任何其他文件的情况下将其赋予该文件，可以通过管道传入。
对于密钥位于 `/etc/billing` 的 billing 服务（这台机器上并没有 billing 服务），操作如下所示：

```bash
read -rsp 'API key: ' api_key
printf 'API_KEY=%s\n' "$api_key" | sudo install -m 640 -o root -g billing /dev/stdin /etc/billing/api.env
unset api_key
```

- `read -rsp 'API key: ' api_key` 会显示提示符（`-p`）、隐藏输入内容（`-s`）、原样保留所有反斜杠（`-r`），并将值存储在 shell 变量 `api_key` 中。你的 shell 历史记录只会记录该命令行，绝不会记录输入的值。
- `printf` 将值填入 `%s` 的位置，并以 `\n` 结尾，因此它将 `API_KEY=` 和密钥打印为一行。
- `|` 将该输出作为 `sudo install` 的输入。`install` 只能从文件名进行复制，而 `/dev/stdin` 是一个代表“该命令自身输入”的文件名，因此管道中的行会成为 `api.env` 的内容。如果改用临时文件，则会在磁盘上多出一份权限为 644 的密钥副本，随后你还必须找到并删除它。
- `unset api_key` 在文件写入后删除该变量。

切勿将密码作为命令的一部分直接输入，例如 `printf 'API_KEY=abc123\n' | ...`。
Bash 会保留你输入的命令行并将其写入 `~/.bash_history`。

### 锁定 /etc/reports

- 将 `db.env` 的所有者设为 root，所属组设为 reports，权限模式设为 640，并保持其内容完全不变。在它的权限为 644 时，每个账户都能读取它，因此该密码也需要更换为新值，不过那是另一项任务了。
- 使用 `sudo rm` 删除 `db.env.bak`。将其移动到 `/tmp` 或其他任何地方都会保留该密码的副本。
- 使用 `install` 管道为 reports 服务的 SMTP 密码创建 `/etc/reports/smtp.env`：单行内容，包含 `SMTP_PASSWORD=` 及紧随其后由你自选的不含空格的密码，所有者设为 root，所属组设为 reports，权限模式设为 640。
- 将 `/etc/reports` 的所有者设为 root，所属组设为 reports，权限模式设为 750。

一旦该文件夹的权限设为 750，你自己的账户就属于最后一位数字所代表的 others，因此无法列出或进入 `/etc/reports`：请使用 `sudo` 和完整路径运行每个命令。
完成后，不带 `sudo` 运行 `ls /etc/reports` 应该会提示 Permission denied 并失败，这也是 reports 组之外的每个账户现在会看到的结果。
