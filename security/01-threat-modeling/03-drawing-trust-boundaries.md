一家在线商店将陌生人输入的订单保存到存放所有客户地址的同一个数据库中。
在这一路径上的某个位置，数据会跨越一个**信任边界**（trust boundary）：即系统中具有不同信任级别的部分之间的分界线。
位于受信侧的组件会在将跨越边界传向它的任何内容进一步传入之前对其进行检查（检查是谁发送的，以及它是否有效）。
这条分界线是系统设计的一部分，而不是具体的硬件设备：网络防火墙可以根据地址和端口拒绝连接，但它无法检查连接中所携带的订单内容。

信任边界也不一定非得沿着两个网络之间的分界线分布。
订单服务（order service）与数据库共享同一个网络，但该服务处理的是源自陌生人浏览器的请求，精心构造的恶意订单可能会诱骗它向数据库发送意料之外的查询。
该查询是携带着订单服务自身的有效凭证到达的，因此仅检查连接发起者并不能阻止它。
在这两者之间仍然存在一条边界，并且数据库处于受信的一侧：它只接受来自订单服务的连接，并拒绝订单服务的数据库账号无权执行的任何查询。
正是这第二道检查限制了被诱骗的服务能够读取或更改的数据范围。

面板上的网络区域（network zone）展示了组件运行的位置以及覆盖它的网络策略（即允许什么连接到什么）。
该策略与组件自身的检查共同保护着组件的安全。
在这家商店中，各区域之间的每条分界线也同时是一个信任边界：

- **internet** 包含商店未运行的所有内容。
- **public network** 是互联网唯一允许连接的区域。
- **private network** 仅接受来自网关（gateway）的连接。

商店运行 API gateway、order service 和 order database。
浏览器运行在客户的计算机上，而支付服务商（payment provider）则由另一家公司运行。

公网和私网各自只有一个入口。
只有 order service 会与数据库通信：如果网关也能查询数据库，就会在私网中打开第二条通路，从而跳过 order service 的检查。
浏览器也绝不能直接连接到数据库（即使只是读取也不行）：否则数据库凭证就会留在浏览器端，任何人都可以复制。

身处私网之内并不意味着数据就是安全的。
网关可以检查订单的发送者以及格式是否良好，但其中的价格仍然是浏览器发送的任何内容，因此 order service 会将订单视为不可信输入，并自行查询价格，而不是直接从请求中读取价格。
支付服务商的回复同样是不可信的，即便该服务商是商店所选择的。
order service 调用服务商进行扣款，回复会通过同一个连接跨越边界返回，因此服务在将订单标记为已支付之前，会先检查回复中注明的订单和金额是否匹配。

### 动手构建

在此画板上，绘制在另一个区域内的区域会被视为其一部分，因此请将这三个区域并排放置，不要将任何一个区域嵌套在另一个区域内。
区域仅用于标记网络边界，因此 order service 与数据库之间的信任边界没有属于自己的区域线条：这两个模块共享同一个区域。
浏览器对应 Client / User 模块，支付服务商对应 External API，order service 对应 Service，order database 对应 Database (SQL)。
根据运行主体和上述区域策略放置各个模块，然后仅绘制每个组件所需的连接，且不要绘制多余的连接，每条连接都应从发起调用的组件开始。
