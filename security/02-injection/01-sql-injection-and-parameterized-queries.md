当代码通过把输入粘贴到查询文本（数据库解析的 SQL 字符串）中来构建 SQL 查询时，输入就可以改变查询的行为。
用 C# 编写的登录代码用用户提交的电子邮件就是这样做的：

```csharp
var sql = "SELECT id FROM users WHERE email = '" + email + "'";
using var cmd = new SqlCommand(sql, connection);
```

对于 `ana@example.com`，拼接后得到 `WHERE email = 'ana@example.com'`，这正是开发者想要的查询。
但 `email` 是不可信的输入（untrusted input）：发送者可以选择每一个字符，而在 SQL 中，单引号会结束一个字符串字面量。
如果有人输入 `' OR '1'='1`，就会生成这样的查询文本：

```sql
SELECT id FROM users WHERE email = '' OR '1'='1'
```

输入中的第一个引号关闭了代码打开的字符串，因此被比较的电子邮件是空的。
输入的其余部分被解析为 SQL：`OR '1'='1'` 添加了一个对每一行都为真的条件（代码追加的那个引号补全了最后的 `'1'`），于是查询返回了所有用户的 id。
这就是 **SQL 注入**（SQL injection）：粘贴到查询文本中的输入成为了查询的一部分，数据库无法区分哪些字符是开发者写的，哪些来自请求。
OWASP 将其列在 A05:2025 Injection 之下。
`SqlCommand` 无法撤销这一点。
它在 `sql` 中接收到的是已经完成的字符串，并原样发送，不会转义任何内容。

没有被引号包围的值也会以同样的方式被粘贴。
订单查询是一个按数字 id 查找订单的端点，它像请求中的所有值一样，以文本形式从查询字符串中读取 id，并通过 C# 字符串插值把它放进 SQL：

```csharp
string id = Request.Query["id"];
var sql = $"SELECT * FROM orders WHERE id = {id}";
```

插值在任何数据库代码看到字符串之前，就用 `id` 的内容替换了 `{id}`，所以它与 `"... WHERE id = " + id` 这种拼接是一回事。
当 `id` 被设为 `0 OR 1=1` 时，数据库收到的是 `WHERE id = 0 OR 1=1`。
这里不需要关闭任何引号，因为输入从来不在字符串字面量之内。
`OR 1=1` 对每一行都为真，所以所有订单都会被返回。
从请求到数据库之间，没有任何环节检查 id 是否为数字，而且这个查询是合法的 SQL，所以它会运行。

### 参数化查询

修复方法是让输入远离查询文本。
**参数化查询**（parameterized query）在查询文本中每个值的位置放一个**占位符**（placeholder），而值则单独传递。
在 `SqlCommand` 中，占位符是以 `@` 开头的名称，由 `Parameters.AddWithValue` 提供它的值，这称为将值绑定（binding）到占位符：

```csharp
var sql = "SELECT id FROM users WHERE email = @email";
using var cmd = new SqlCommand(sql, connection);
cmd.Parameters.AddWithValue("@email", email);
```

现在对每个请求来说，查询文本都是相同的。
SqlClient 是 `SqlCommand` 所属的库，它把该文本和值作为独立的部分发送给数据库，数据库在读取值之前就已经解析了查询。
`@email` 被解析为放置一个值的位置，所以输入只能填充这个位置。
其中的引号只是电子邮件的一个字符：`' OR '1'='1` 会被整体与每个用户的电子邮件进行比较，一个也不匹配，查询不返回任何行。
请原样传递收到的值；自己把其中的引号加倍会改变被比较的电子邮件。

![输入 `' OR '1'='1` 以两种方式用于登录查询。拼接时，它把查询变成 `WHERE email = '' OR '1'='1'`，对每个用户都为真；参数化时，查询文本保留 `@email`，输入作为一个值单独发送，不匹配任何账户。](images/query-structure-vs-data.png)

拼接时，输入的第一个引号结束了电子邮件字符串，其余部分被解析为 SQL，而参数化查询则把相同的字符作为一个值来接收。

产品列表是一个使用 node-postgres 客户端（`pg`）的 Node.js 端点，它给占位符编号：`$1` 是值数组中的第一项，`$2` 是第二项。

```js
const { rows } = await client.query(
  'SELECT id, name, price FROM products WHERE category = $1',
  [category]
);
```

node-postgres 同样把查询文本和值分开发送。
其他数据库的一些驱动则是在客户端把每个值写入语句中，自行对其转义，然后发送一个字符串。
无论哪种方式，你的代码看起来都一样，并且在两种情况下，值都不会变成 SQL 代码。
占位符可以放在查询使用值的任何地方，例如 `WHERE` 比较中的电子邮件或订单 id，或者 `INSERT` 或 `UPDATE` 的值。

保留拼接的那些修复方法，是试图在输入仍留在查询文本中的同时使其无害，而每一种都有漏洞。
把每个引号加倍（`'` 变为 `''`）只能保护位于引号内的值，所以上面的订单 id 完全得不到保护。
转义规则在不同数据库之间也不同，而代码中只要有一处忘记转义就会重新打开漏洞，所以手动转义是最后的手段，绝不能替代参数。
拒绝包含引号、空格或单词 `OR` 的输入，会拒绝像 `o'neil@example.com` 这样的真实地址，而且 SQL 还有其他写条件的方式，是这样的列表没有列出的。
把值包在额外的引号里，只是改变了输入关闭字符串所需的引号数量。

存储过程（stored procedure）的安全性取决于它所运行的 SQL。
应用程序可以把电子邮件作为参数传递给存储过程，而把它用作 `WHERE email = @email` 的存储过程会使其保持为一个值。
下面这个存储过程把登录代码中的拼接移到了数据库内：

```sql
CREATE PROCEDURE find_user @email nvarchar(256) AS
EXEC('SELECT id FROM users WHERE email = ''' + @email + '''');
```

在 T-SQL 字符串中，`''` 代表一个引号字符。
`EXEC` 会运行其字符串中包含的任何 SQL，而该字符串在每次存储过程运行时构建，其中粘贴了 `@email`，所以它没有任何内容是提前编译的。
`' OR '1'='1` 改变这个查询的方式，与它改变那个 C# 查询的方式完全一样。
参数保护的是值进入存储过程的途中；存储过程接下来对它做什么，决定了其余的一切。

### 排序列和允许列表

产品列表还允许调用者选择排序列，它通过 `sortColumn` 从查询字符串中传入。
如果把它拼接在 `ORDER BY` 之后，它就和电子邮件一样，是查询文本中的不可信输入，而携带的内容超出列名的值会向查询中添加 SQL。

占位符无法修复这个问题。
占位符代表的是值，而列名是**标识符**（identifier），即表或列的名称，是查询结构的一部分。
`ORDER BY $1` 配合 `[sortColumn]` 会把调用者的文本（比如 `price`）绑定为一个值：一个常量字符串，对每一行都相同。
根据数据库的不同，查询随后会按该常量排序，这会使行没有任何有用的顺序，或者以错误失败。
它绝不会按 price 列排序。
值中的双引号也不会把它变成标识符：绑定的值永远不会被解析为 SQL，所以它们只是另外两个字符。

标识符需要**允许列表**（allowlist）：一个固定的、写在代码中的列表，列出调用者可以选择的列名。
输入只是从中选择一个条目：

```js
const sortable = ['name', 'price', 'created_at'];
const column = sortable.includes(sortColumn) ? sortColumn : 'name';
const sql = 'SELECT id, name, price FROM products ORDER BY ' + column;
```

查询文本中仍然包含一个列名，但始终是代码所写的三个字符串之一。
任何其他值都会回退到 `name`；端点也可以改为拒绝该请求。
仅仅把 `sortColumn` 放在双引号中（SQL 引用标识符的方式）是不够的：输入中的双引号会关闭被引用的标识符，就像单引号关闭字符串一样。
转义输入中的双引号可以阻止这一点，但转义标识符遵循的规则与转义字符串值不同，所以很容易出错。
即使转义正确，调用者仍然可以按表中的任何列排序，包括页面从不显示的列，例如成本价：行的顺序随后会揭示哪些产品成本最高。
允许列表则没有这两个问题。
长度限制完全没有帮助：很短的值就足以改变查询，就像 `0 OR 1=1` 这八个字符对订单查询所做的那样。
